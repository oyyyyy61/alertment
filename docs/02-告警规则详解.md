# 02 告警规则详解

全部规则位于 [`manifests/prometheus-rules.yaml`](../manifests/prometheus-rules.yaml)，
共 6 个规则组、1 条 recording rule、27 条告警规则。本文按组解释每条规则的**触发条件、
恢复语义与设计动机**。

先统一几个概念：

- **生命周期告警**：表达式描述"资源存在"，资源出现时 `firing`、消失时 `resolved`，
  飞书里是"开始/结束"一对消息（`GPUStackModelInstanceLoaded`、`GPUResourceInUse`、
  `KubernetesGPUAllocationActive`、`GPUProcessStarted`）。
- **阈值告警**：指标越过阈值持续 `for` 时长才触发，回落后恢复
  （温度、显存、磁盘、排队等）。
- **事件告警**：对计数器求增量，>0 即触发，短时爆发型（XID、请求失败、驱逐）。
- 所有规则都带 `category` 标签——它既是消息分类，也是 AlertmanagerConfig 的
  通知过滤条件（只送 `category=~.+` 的告警进飞书）。

## 1. gpustack.worker —— GPUStack 平台层

| 告警 | 表达式（缩写） | for | 语义 |
| --- | --- | --- | --- |
| GPUStackWorkerMetricsDown | `up{job="gpustack-worker-discovery"} == 0` | 2m | 某个 Worker 指标端点挂了 |
| GPUStackWorkerDiscoveryMissing | `absent(up{job="gpustack-worker-discovery"})` | 5m | HTTP SD 一个 Worker 都没发现，多半是 Server 的 10161 出问题 |
| GPUStackServerMetricsDown | `up{job="gpustack-server"} == 0` | 2m | Server 指标端口不可达 |
| GPUStackWorkerRootFilesystemHigh | `gpustack:worker_node_filesystem_utilization_rate{mountpoint="/"} > 95` | 10m | Worker 根分区将满，可能引发镜像 GC 风暴或驱逐 |
| GPUStackGPUHighTemperature | `gpustack:worker_node_gpu_temperature_celsius > 82` | 5m | GPUStack 视角的整机温度 |
| GPUStackModelInstanceLoaded | 见下文 | 1m | 模型实例生命周期：真正运行中 = 已加载 |
| GPUStackRequestErrors | `increase(gpustack:request_success_total{finished_reason=~"error\|abort"}[5m]) > 0` | 即时 | 5 分钟内出现失败/中止请求 |
| GPUStackRequestQueueBacklog | `gpustack:num_requests_waiting > 0` | 10m | 请求持续排队，扩容或换卡信号 |
| GPUStackUnattributedWorkerUse | GPU 利用率 >20% 且 `unless on(worker_name)` 无任何 `num_requests_running` 序列 | 10m | GPU 在忙但没有模型实例认领——调度盲区信号 |

### GPUStackModelInstanceLoaded 的"真在跑"门控（重点）

```promql
count by (worker_name, model_name, model_instance_name, runtime) (
  gpustack:num_requests_running
) > 0
and on (model_name)
max by (model_name) (gpustack:model_running_instances) >= 1
```

**为什么不能只写第一段？** 实测发现 GPUStack Worker 在模型停止/暂停后，仍会持续
暴露该实例的 `gpustack:num_requests_running`（值 0）残留序列——"序列存在"不等于
"实例在跑"。告警一度在模型完全停止的情况下持续触发"资源已分配"。

修复思路：Worker 侧序列提供**实例级标签**（worker/model/instance/runtime），Server 侧
`gpustack:model_running_instances`（GPUStack 自己统计的运行中实例数）提供**真值
门控**，两者 `and on (model_name)` 连接。效果：

- 模型部署中/下载权重：`model_running_instances=0`，不告警；
- vLLM 起来、GPUStack 确认 Running：告警 firing"已加载"；
- 模型停止：告警 resolved"已卸载/已停止"，与 description 的恢复语义一致。

## 2. dcgm.hardware —— GPU 硬件层

| 告警 | 表达式（缩写） | for | 语义 |
| --- | --- | --- | --- |
| DCGMExporterDown | `up{namespace="gpu-observability", service="dcgm-exporter"} == 0` | 2m | 硬件与归属指标断供 |
| GPUXIDError | `increase(DCGM_EXP_XID_ERRORS_TOTAL[5m]) > 0 or DCGM_EXP_XID_ERRORS_COUNT > 0` | 即时 | XID 错误，看内核/DCGM 日志再决定是否下线 GPU |
| GPUHealthWarning | `DCGM_EXP_GPU_HEALTH_STATUS > 0` | 1m | DCGM 健康检查失败（10=警告 20=失败） |
| DCGMGPUHighTemperature | `DCGM_FI_DEV_GPU_TEMP > 85` | 5m | 硬件视角高温（比 GPUStack 阈值高 3 度，两级告警） |
| DCGMGPUMemoryNearlyFull | `100 * FB_USED / clamp_min(FB_USED+FB_FREE,1) > 95` | 10m | 显存接近耗尽 |
| GPUResourceInUse | `DCGM_FI_DEV_FB_USED{pod!="", namespace!=""} > 512` | 1m | **k8s Pod 生命周期**：Pod 开始/停止使用 GPU |
| GPUHostUseUnattributed | `DCGM_FI_DEV_FB_USED{pod=""} > 512` | 5m | **宿主机进程占用**：调度器看不见的"暗物质" |
| GPUAllocatedButIdle | `DCGM_FI_DEV_GPU_UTIL{pod!="", namespace!=""} < 5` | 15m | 分给 Pod 却闲置——资源回收线索 |
| GPUDoubleBitECCError | `increase(DCGM_FI_DEV_ECC_DBE_AGG_TOTAL[5m]) > 0` | 即时 | 不可纠正 ECC，应迁移负载 |

`pod!=""` 与 `pod=""` 的一对告警是这套方案的精髓：dcgm-exporter 配置了 Pod 标签
采集后，**同一张卡上 k8s 管的进程和宿主机原生进程能按 label 切开**，两个视角分别
告警，"逻辑空闲、实际满载"的调度盲区无所遁形。

## 3. kubernetes.gpu-allocation —— 调度视角

`KubernetesGPUAllocationActive`（for: 1m，生命周期）：

```promql
sum by (namespace, pod) (kube_pod_container_resource_requests{resource=~"nvidia(_com|\\.com)_gpu"} > 0)
  * on (namespace, pod) group_left (node) max by (namespace, pod, node) (kube_pod_info{node!=""})
  and on (namespace, pod) max by (namespace, pod) (kube_pod_status_phase{phase="Running"} == 1)
  * on (namespace, pod) group_left (label_observability_gpustack_io_owner, ...)
    max by (namespace, pod, ...) (kube_pod_labels) > 0
```

三层连接：GPU request > 0 × Pod 已调度到节点 × Pod 处于 Running ×（展开归属标签）。
Pod 起来告警"分配已生效"（事件：资源已分配），Pod 结束告警恢复。与
`GPUResourceInUse`（真实显存视角）、`GPUProcessStarted`（宿主机进程视角）互为印证。

## 5. gpu.processes —— 宿主机进程生命周期（重点）

```promql
# GPUProcessStarted（for: 30s，生命周期）
max_over_time(gpu_process_used_memory_mib{scope="host"}[1m]) >= 0

# GPUProcessLongRunning（for: 1m）
time() - max_over_time(gpu_process_start_time_seconds{scope="host"}[1m]) > 18000
```

`GPUProcessStarted` 的写法值得体会：`>= 0` 恒真，**本质是"序列存在性检测"**——
exporter 报出新进程序列后 30 秒即 firing（摘要带 owner/task/PID/启动时间/显存），
进程退出序列消失即 resolved（适配器渲染出运行时长）。每条序列自带
`owner`（系统用户）与 `task`（脚本名）标签，告警天然带人。

### 开始/结束消息几乎同时到达的问题（重点）

场景：任务 A 结束后立刻启动任务 B（同名脚本、同一用户）。A 的 resolved 与 B 的
firing 在几秒内先后到达飞书，两条消息乍看一模一样。两层修复：

1. **适配器横幅**（见 docs/03）：消息首行直接写
   `【GPU 任务·开始 🟢】`/`【GPU 任务·结束 🔴】`/`【GPU 任务·切换 🔄】`（混合组）。
2. **接续提示**：结束消息发送时适配器查一次
   `group by (pid) (gpu_process_used_memory_mib{scope="host",node=...,task=...})`，
   若同任务已有新 PID 在跑，就在结束消息里注明"本条已结束对应旧进程 PID x，
   随后的开始通知属于新进程 PID y"。Prometheus 查询失败时静默跳过。

路由侧（AlertmanagerConfig）的配合：`GPUProcessStarted` 子路由
`groupBy: [alertname, cluster, node, owner, task, pid]`——PID 进分组键，不同进程
互不合并；`groupWait: 0s`、`groupInterval: 30s` 保证秒级送达；`repeatInterval: 24h`
避免长任务重复打扰（长时间运行的提醒交给 `GPUProcessLongRunning` 每 5 小时一次）。

## 6. training.progress —— 训练进度

recording rule `gpu_training_progress_percent` = `100 * current_step /
clamp_min(total_steps, 1)`（按 owner/team/project/task 维度）。

| 告警 | 表达式（缩写） | for | 语义 |
| --- | --- | --- | --- |
| GPUTrainingStalled | `current_step < total_steps and changes(current_step[15m]) == 0` | 15m | 训练没跑完但步数 15 分钟没动 |
| GPUTrainingCompleted | `current_step >= total_steps` | 1m | 步数达标，事件：任务已完成 |

前置约定：训练程序要在 `/metrics` 暴露 `training_current_step` /
`training_total_steps` 等 gauge（带 owner/project/task 标签），Pod 打
`observability.gpustack.io/progress: "true"` 标签并声明名为 `metrics` 的端口，
PodMonitor 自动发现。

## 7. 修改规则的流程

```bash
# 1. 改 manifests/prometheus-rules.yaml
# 2. 语法与效果先在 Prometheus 上试跑（UI 或 API）：
curl -sG http://127.0.0.1:9090/api/v1/query --data-urlencode 'query=你的新表达式'
# 3. 应用（prometheus-operator 会在约 1 分钟内自动重载）
kubectl apply -f manifests/prometheus-rules.yaml
# 4. 观察 http://127.0.0.1:9090/alerts 的 Pending/Firing 状态
```

改动告警的 `labels`（包括 expr 产生的实例标签）会改变告警指纹，已 firing 的告警会
先 resolved 再重新评估，飞书可能收到一对"恢复+触发"消息，属正常现象。
