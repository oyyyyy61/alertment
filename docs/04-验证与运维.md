# 04 验证与运维

## 1. 部署体检

```bash
./verify.sh
```

脚本依次检查：节点、monitoring 命名空间 Pod、gpu-observability 的全部 CR
（ServiceMonitor/PodMonitor/ScrapeConfig/PrometheusRule）、dcgm-exporter 与
gpu-process-exporter 的 rollout 状态、Kueue ServiceMonitor、HTTP SD 发现配置。

## 2. 打开三个 UI

```bash
kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80
kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090:9090
kubectl -n monitoring port-forward svc/kube-prometheus-stack-alertmanager 9093:9093
```

Grafana 管理密码（deploy.sh 随机生成）：

```bash
kubectl -n monitoring get secret gpu-grafana-admin \
  -o jsonpath='{.data.admin-password}' | base64 -d && echo
```

排查告警链路时按顺序看：

```text
http://127.0.0.1:9090/targets   数据源是否都 up（Worker 发现 4 个 target）
http://127.0.0.1:9090/rules     规则是否加载、有无解析错误
http://127.0.0.1:9090/alerts    告警 Inactive→Pending→Firing 状态
http://127.0.0.1:9093/#/alerts  Alertmanager 是否收到、路由分组是否正确
```


## 4. 端到端测试

### 4.1 链路测试（合成告警）

模拟 Alertmanager 的 webhook 请求发到适配器，验证"翻译 + 飞书投递"：

```bash
kubectl -n gpu-observability run feishu-alert-test \
  --rm -i --restart=Never --image=curlimages/curl:8.12.1 -- \
  curl -fsS -H 'Content-Type: application/json' \
  --data '{"status":"firing","commonLabels":{"alertname":"FeishuDeliveryTest","cluster":"gpustack-rke2"},"alerts":[{"status":"firing","labels":{"alertname":"FeishuDeliveryTest","severity":"info","category":"test","node":"gpu-node-15"},"annotations":{"summary":"GPU 中文告警投递测试"},"startsAt":"2026-10-11T00:00:00Z"}]}' \
  http://alertmanager-feishu-adapter:8080/alerts
```

测试 Pod 自动清理。返回 `200 ok` 且飞书群收到消息即成功。

### 4.2 真实告警演练

安全做法：把某个学习用负载停掉观察生命周期告警（演示完恢复），例如：

```bash
kubectl -n gpu-observability logs deployment/alertmanager-feishu-adapter --tail=50
# 观察真实告警：在 GPU 节点跑一个短任务，飞书应收到 开始/结束 一对消息
nvidia-smi dmon -s u   # 另一终端观察利用率变化
```

故障注入后观察顺序：Prometheus `/alerts` 先 Firing → Alertmanager 收到 → 飞书
收到消息 → 修复后收到"已恢复"。

## 5. 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 飞书收不到消息，适配器日志 502 | webhook URL 错或签名密钥不匹配；在飞书机器人设置里核对，Secret 重新 apply |
| 飞书返回签名错误 | Pod 时钟偏差或签名算法问题；核对 `string_to_sign = f"{timestamp}\n{secret}"` |
| Watchdog 等无关告警进飞书 | AlertmanagerConfig 根路由靠 `category=~.+` 过滤；新告警规则必须带 `category` 标签 |
| 自定义 AlertmanagerConfig 不生效 | `values/kube-prometheus-stack.yaml` 里 `alertmanagerConfigMatcherStrategy: type: None` 必须保留；且 CR 要带 `observability.gpustack.io/receiver: gpu-alerts` 标签 |
| 模型已停止仍报"模型实例已加载" | 检查规则是否含 `gpustack:model_running_instances >= 1` 门控（docs/02 第 1 节）；这是 GPUStack Worker 残留序列导致的经典误报 |
| 开始/结束消息分不清 | 确认适配器镜像滚动重启过（ConfigMap 改动不会自动重启 Pod）：`kubectl -n gpu-observability rollout restart deployment/alertmanager-feishu-adapter` |
| 四个平台组件 TargetDown 常驻 | values 里已关闭 kubeControllerManager/kubeScheduler/kubeEtcd/kubeProxy 抓取；新环境必须带上 |
| Worker 扩缩容后指标没跟上 | `gpustack-worker-discovery` 用 HTTP SD 每分钟刷新 `/metrics/targets`，最多等 1 分钟 |
| GPU 活动多但无归属告警 | 检查 Pod 是否带 `observability.gpustack.io/*` 标签，且 kube-state-metrics 的 `metricLabelsAllowlist` 包含它们 |
| 适配器只读文件系统报错 | 正常设计；它不写盘，日志走 stdout（`kubectl logs`） |

## 6. 运维手册：这块 GPU 谁在用

完整命令见 [`runbooks/who-is-using-gpu.md`](../runbooks/who-is-using-gpu.md)。三个
视角要一起看——Kubernetes Pod、GPUStack 推理请求、宿主机桌面进程的"主人"各不相同：

```promql
# 1. k8s 视角：哪张卡分给了哪个 Pod
count by (node, gpu, namespace, pod) (DCGM_FI_DEV_FB_USED{pod!=""}) > 0

# 2. GPUStack 视角：哪个模型实例在跑
count by (worker_name, model_name, model_instance_name) (gpustack:num_requests_running)

# 3. 宿主机视角：哪个系统用户/脚本在跑（含调度器看不见的进程）
gpu_process_used_memory_mib{scope="host"}
```

GPUStack 的用量/计费走 GPUStack Usage API（`/v2/usage/*`，按用户/API key 统计），
见 runbook。
