# 01 部署指南：从零复现

本文是从零复现整条"监控 → 告警 → 飞书"链路的完整步骤。每一步都给出命令与
原因说明。

## 0. 前置条件

| 组件 | 要求 |
| --- | --- |
| Kubernetes 集群 | RKE2（或任意支持 monitoring.coreos.com CRD 的集群），本方案针对 GPUStack v2 集群 |
| GPU 节点 | 已装 NVIDIA 驱动与 nvidia-container-runtime（dcgm-exporter 用 `runtimeClassName: nvidia`） |
| GPUStack | v2.x，Server 暴露 10161（含 `/metrics/targets`），Worker 暴露 10151 |
| 存储 | Longhorn（Prometheus/Alertmanager/Grafana 持久化，可在 values 里替换） |
| 本机工具 | kubectl、helm 3、openssl |
| 网络 | 能访问 prometheus-community 与 NVIDIA Helm 仓库（离线方式见第 3.3 节） |

涉及的 Helm Chart 版本经本包渲染验证：

- `kube-prometheus-stack` 92.1.1
- `dcgm-exporter` 4.8.4

## 1. 获取目标集群管理员 kubeconfig

RKE2 在每个 server 节点生成 `/etc/rancher/rke2/rke2.yaml`。先在目标节点验证集群，
再拷贝 kubeconfig 到本机（示例以 `.11` 为准，`.12` 同理替换 IP）：

```bash
export RKE2_SSH_USER=你的ssh用户

# 验证集群节点
ssh "${RKE2_SSH_USER}@192.168.50.11" \
  'sudo env KUBECONFIG=/etc/rancher/rke2/rke2.yaml \
  /var/lib/rancher/rke2/bin/kubectl get nodes -o wide'

# 节点上生成临时副本并拷回本机
ssh "${RKE2_SSH_USER}@192.168.50.11" \
  'sudo install -m 600 -o "$(id -un)" -g "$(id -gn)" \
  /etc/rancher/rke2/rke2.yaml /tmp/gpustack-rke2.yaml'
mkdir -p "$HOME/.kube" && chmod 700 "$HOME/.kube"
scp "${RKE2_SSH_USER}@192.168.50.11:/tmp/gpustack-rke2.yaml" \
  "$HOME/.kube/gpustack-rke2.yaml"
chmod 600 "$HOME/.kube/gpustack-rke2.yaml"
ssh "${RKE2_SSH_USER}@192.168.50.11" rm -f /tmp/gpustack-rke2.yaml

# RKE2 默认监听 127.0.0.1:6443，改成节点 IP
sed -i 's#https://127.0.0.1:6443#https://192.168.50.11:6443#' \
  "$HOME/.kube/gpustack-rke2.yaml"
```

验证身份与目标，**两项权限检查必须都输出 yes**：

```bash
export KUBECONFIG="$HOME/.kube/gpustack-rke2.yaml"
kubectl config current-context
kubectl get nodes -o wide
kubectl auth can-i create namespaces
kubectl auth can-i create customresourcedefinitions.apiextensions.k8s.io
```

> 注意：该 kubeconfig 内嵌 cluster-admin 客户端证书与私钥，权限 600、不进聊天记录、
> 不进 Git。如果 API 证书不含 `192.168.50.11`，用证书里的主机名并在 `/etc/hosts`
> 做映射；不要用 `insecure-skip-tls-verify`。

## 2. 一键部署监控栈

```bash
cd alertment
export KUBECONFIG="$HOME/.kube/gpustack-rke2.yaml"
./deploy.sh
```

`deploy.sh` 依次完成（脚本内容不多，建议通读一遍再执行）：

1. **检查目标**：节点列表必须包含 `gpustack-cp01/cp02`、`gpu-node-14/15`，防止把
   栈装错集群；`kubectl auth can-i` 复核权限。
2. **安装 kube-prometheus-stack**：使用 `values/kube-prometheus-stack.yaml`——
   - 组件全部钉在控制面节点（`node-role.kubernetes.io/control-plane`）；
   - Prometheus 30 天 / 80GB 保留，Longhorn 100Gi 存储，全局外标签
     `cluster: gpustack-rke2`；
   - **关闭 RKE2 上默认不可达的组件抓取**（kubeControllerManager/kubeScheduler/
     kubeEtcd/kubeProxy），否则四个 TargetDown 告警会常驻；
   - **Alertmanager 的 `alertmanagerConfigMatcherStrategy: type: None`**：允许
     AlertmanagerConfig 按自定义标签路由而不被强制附加 namespace 匹配器；
   - **AlertmanagerConfig 选择器**：只加载带
     `observability.gpustack.io/receiver: gpu-alerts` 标签的 AlertmanagerConfig；
   - **kube-state-metrics 允许列表**：把 Pod 的
     `observability.gpustack.io/owner|team|project|task`、`kueue.x-k8s.io/queue-name`
     标签暴露成指标标签（归属告警的前提）；
   - Grafana 管理密码存入随机生成的 `gpu-grafana-admin` Secret。
3. **应用 manifests（kustomize）**：Namespace、GPUStack 抓取、告警规则、面板、
   训练进度 PodMonitor、Kueue ServiceMonitor、gpu-process-exporter。
4. **安装 dcgm-exporter**：只调度到两个 GPU 节点，带 Pod 归属标签采集与完整硬件/
   错误指标（`values/dcgm-exporter.yaml`）。

### 2.1 部署了哪些采集源（对应架构图的采集层）

| 清单 | 作用 |
| --- | --- |
| `manifests/gpustack-workers.yaml` | ServiceMonitor 抓 GPUStack Server `:10161/metrics`；ScrapeConfig 用 **HTTP SD**（`/metrics/targets`）每分钟自动发现所有 Worker `:10151`，Worker 扩缩容无需改配置 |
| `manifests/gpu-process-exporter.yaml` | DaemonSet 跑在 GPU 节点，`hostPID` 进入宿主机命名空间读 `/proc`，把每个 CUDA 进程的 **系统用户/任务脚本/PID/启动时间/显存** 导出为 `gpu_process_*` 指标（scope=host）；两个容器协作：nvidia-collector 采数据、exporter 提供带 60s 缓存的 metrics 端点 |
| `manifests/kueue-servicemonitor.yaml` | 抓 `gpustack-system` 里 Kueue 的 https 指标（排队/驱逐） |
| `manifests/training-progress-podmonitor.yaml` | 按 `observability.gpustack.io/progress: "true"` 标签自动发现训练任务的 `/metrics`（步数/epoch） |
| `values/dcgm-exporter.yaml` | DCGM 自定义指标列表含 XID、ECC、健康检查、显存三段（used/free/reserved），GeForce 不支持的字段自动跳过 |

### 2.2 验证部署

```bash
./verify.sh
kubectl -n monitoring get pods
kubectl -n gpu-observability get pods,servicemonitor,podmonitor,scrapeconfig,prometheusrule
```

Prometheus 里确认目标健康（应看到 gpustack-server、gpustack-worker-discovery 各
4 个 target、dcgm-exporter、gpu-process-exporter 等）：

```bash
kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090:9090
# 浏览器打开 http://127.0.0.1:9090/targets
```

## 3. 配置飞书通知

### 3.1 创建飞书自定义机器人

1. 在目标飞书群：**群设置 → 群机器人 → 添加机器人 → 自定义机器人**。
2. 勾选**签名校验**（强烈建议），复制 **webhook 地址** 与 **签名密钥**。
3. 两个值都不落盘、不进 Git，下一步直接输入。

### 3.2 创建 Secret 并部署适配器

```bash
read -rsp 'Feishu webhook URL: ' FEISHU_WEBHOOK && echo
read -rsp 'Feishu signing secret: ' FEISHU_SECRET && echo
kubectl -n gpu-observability create secret generic feishu-gpu-alerts \
  --from-literal=webhook-url="$FEISHU_WEBHOOK" \
  --from-literal=signing-secret="$FEISHU_SECRET" \
  --dry-run=client -o yaml | kubectl apply -f -
unset FEISHU_WEBHOOK FEISHU_SECRET

kubectl apply -f examples/feishu-adapter.yaml
kubectl apply -f examples/alertmanagerconfig-feishu.yaml
kubectl -n gpu-observability rollout status \
  deployment/alertmanager-feishu-adapter --timeout=2m
```

说明：

- `examples/feishu-adapter.yaml` 是 **ConfigMap（内含完整 adapter.py）+
  Deployment（2 副本）+ Service** 的单文件部署。容器镜像就是 `python:3.12-alpine`，
  无第三方依赖；只读根文件系统、非 root、drop ALL capabilities。
- `examples/alertmanagerconfig-feishu.yaml` 是 Alertmanager 的接收器：
  - 根路由 `matchers: category=~.+` —— 只有带 `category` 标签的告警才进飞书，
    `Watchdog` 等常驻告警被天然过滤；
  - 生命周期子路由 `GPUProcessStarted` 按 `[alertname, cluster, node, owner, task,
    pid]` 分组、`groupWait: 0s`、`groupInterval: 30s`、`repeatInterval: 24h`，保证
    开始/结束消息秒级送达且长任务不重复打扰；
  - `sendResolved: true` —— 资源释放/模型卸载/进程结束会发"已恢复"消息。
- **只应用一个接收器示例**（feishu 或 webhook），同时应用会重复通知。

### 3.3 离线/受限网络安装

```bash
# 用本地 chart 包跳过仓库更新
KPS_CHART=/path/to/kube-prometheus-stack-92.1.1.tgz \
DCGM_CHART=/path/to/dcgm-exporter-4.8.4.tgz \
./deploy.sh

# 或指定其他版本
KPS_CHART_VERSION=<version> DCGM_CHART_VERSION=<version> ./deploy.sh
```

> kube-prometheus-stack 的默认镜像在国内拉取困难时，values 里 kube-state-metrics
> 已示例使用 `m.daocloud.io` 镜像代理，其余镜像可按同样方式加 registry 前缀。

## 4. 端到端验证

向适配器发一条模拟 Alertmanager 的 webhook 请求（走与真实告警完全相同的集群内路径）：

```bash
kubectl -n gpu-observability run feishu-alert-test \
  --rm -i --restart=Never --image=curlimages/curl:8.12.1 -- \
  curl -fsS -H 'Content-Type: application/json' \
  --data '{"status":"firing","commonLabels":{"alertname":"FeishuDeliveryTest","cluster":"gpustack-rke2"},"alerts":[{"status":"firing","labels":{"alertname":"FeishuDeliveryTest","severity":"info","category":"test","node":"gpu-node-15"},"annotations":{"summary":"GPU 中文告警投递测试"},"startsAt":"2026-10-11T00:00:00Z"}]}' \
  http://alertmanager-feishu-adapter:8080/alerts
```

飞书群收到"【GPU 告警·已触发】飞书告警链路测试"即链路打通。投递失败排查（不会
打印 Secret 内容）：

```bash
kubectl -n gpu-observability logs deployment/alertmanager-feishu-adapter --tail=100
```

常见的两类失败：`502 delivery failed`（webhook URL 或签名错误，看飞书返回码）、
适配器 Pod 不就绪（看 readiness 探针）。

## 5. 可选：节点级配置

`node-config/gpu-node-15-kubelet.conf` 是 GPU 节点的 kubelet 镜像 GC 阈值
（95%/90%），复制为 RKE2 节点 `/etc/rancher/rke2/kubelet.d/20-image-gc-thresholds.conf`
后重启 kubelet 生效。根分区使用率告警 `GPUStackWorkerRootFilesystemHigh` 的阈值与
它对齐。

## 6. 建议的通知策略

| 事件 | 通知方式 |
| --- | --- |
| XID 错误、GPU 健康异常、Worker 掉线 | 立即 |
| 高温、请求错误、磁盘将满 | 立即 |
| GPU 分配/开始使用（生命周期） | 立即（信息级） |
| GPU 释放/模型卸载/进程结束 | "已恢复"消息 |
| 已分配但空闲 GPU | 15 分钟后 |
| Kueue 持续排队 | 15 分钟后 |

至此链路完整可用。后续调优：加/改告警见 docs/02，改消息样式见 docs/03，
排障见 docs/04。
